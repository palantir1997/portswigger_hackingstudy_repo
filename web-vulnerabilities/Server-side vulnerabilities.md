# 웹 보안 취약점 종합 가이드

---

## 1. 서버사이드 취약점 (Server-Side Vulnerabilities)

서버사이드 취약점은 웹 애플리케이션의 **서버 내부에서 실행되는 로직**의 결함을 악용하는 보안 취약점입니다. 사용자가 직접 눈으로 보거나 조작할 수 없는 서버의 백엔드 처리 과정에서 발생하기 때문에, 공격이 성공하면 시스템 전체의 권한을 빼앗기거나 데이터베이스가 유출되는 등 **치명적인 피해**로 이어지는 경우가 많습니다.

### 주요 취약점 유형

#### SSRF (Server-Side Request Forgery)
공격자가 서버를 대리인(Proxy) 삼아 내부망이나 외부로 원치 않는 HTTP 요청을 보내게 만드는 취약점입니다. 외부에서 접근할 수 없는 내부 서버(관리자 페이지 등)를 공격할 때 사용됩니다.

#### SSTI (Server-Side Template Injection)
사용자가 입력한 값이 서버 측 템플릿 엔진(Jinja2, Thymeleaf 등)에 검증 없이 삽입될 때 발생합니다. 이를 통해 서버에서 임의의 명령어(RCE)를 실행할 수 있게 됩니다.

#### 파일 업로드 취약점 (File Upload Vulnerabilities)
공격자가 웹쉘(Web Shell) 같은 악성 스크립트 파일을 서버에 업로드하고 실행하여, 시스템 제어권을 탈취하는 대표적인 서버사이드 결함입니다.

#### 역직렬화 취약점 (Insecure Deserialization)
서버가 신뢰할 수 없는 사용자 입력 데이터를 객체로 역직렬화하는 과정에서 악성 코드가 실행되도록 유도하는 취약점입니다.

## 2. 경로 조작 공격 (Path Traversal)

### 공격 개요
버프 프록시로 이미지 파일 요청을 가로챈 후, 상위 디렉토리로 이동하는 경로 조작을 통해 민감한 파일에 접근할 수 있습니다.

### 실습 예시
```
GET /image?filename=../../../../etc/passwd HTTP/2
```

리피터에서 위와 같은 페이로드를 입력하면 `/etc/passwd` 파일의 전체 내용을 획득할 수 있습니다.

## 3. 접근 제어 취약점 (Access Control)

**접근 제어(Access Control) 취약점**은 사용자가 시스템에서 무엇을 보고 어떤 권한으로 행동할 수 있는지를 서버가 제대로 검증하지 않아 발생하는 취약점입니다.

### 주요 유형

#### 수직적 접근 제어 취약점 (Vertical Access Control)
일반 사용자(User) 권한인 사람이 관리자(Admin)만 쓸 수 있는 기능이나 페이지에 접근하는 경우입니다.

**예시:** 주소창에 `/admin`을 직접 입력했더니 관리자 패널이 뜸

#### 수평적 접근 제어 취약점 (Horizontal Access Control)
같은 권한을 가진 사용자끼리 서로 다른 사람의 데이터에 접근하는 경우입니다.

**예시:** 내 계정 조회 URL인 `/account?id=100`에서 숫자를 `101`로 바꿨더니 타인의 개인정보가 뜸

### 핵심 개념
"이 요청을 보낸 사람이 이 권한을 가져도 되는 사람이 맞는지", "다른 사람의 자원을 훔쳐보려고 요청값을 조작하진 않았는지" 서버가 철저히 확인(검증)하지 않을 때 발생하는 모든 보안 구멍입니다.

## 4. robots.txt 보안

### 개요
**검색엔진 봇(크롤러)에게 웹사이트의 어떤 페이지를 수집하게 할지, 어떤 페이지를 수집하지 말라고 할지(Allow/Disallow)** 그 범위를 지정해주는 파일이 바로 `robots.txt`입니다.

### 보안 위험성

`robots.txt` 자체는 웹사이트 루트에 공개되어 있는 게 정상이기 때문에 '절대 노출되면 안 되는 파일'은 아닙니다. 하지만 **여기에 민감한 경로를 적어두면 보안상 치명적인 위험**이 생깁니다.

### 공격자의 정보 수집 방법

일부 개발자들이 `Disallow: /super-secret-admin-page/` 처럼 **사람들에게 숨기고 싶은 관리자 페이지나 백엔드 경로**를 검색엔진에 안 뜨게 하려고 여기에 적어둔다는 점이 문제입니다.

`robots.txt`는 누구나 주소 뒤에 `/robots.txt`만 붙이면 1초 만에 볼 수 있는 공개 파일이기 때문에, 공격자들은 오히려 이 파일을 먼저 열어보고 **"아, 이 사이트에는 이런 숨겨진 관리자 경로가 있구나"** 하고 타겟팅을 시작합니다.

이는 보안을 은폐에만 의존하는 'Security through obscurity'의 대표적 실패 사례입니다.

## 5. 권한 상승 공격 (Privilege Escalation)

### 5-1. 보호되지 않은 관리자 기능 (Unprotected Admin Functionality)

서버가 관리자 기능에 대한 접근 제어를 제대로 하지 않아 일반 사용자도 접근할 수 있는 취약점입니다.

### 5-2. 요청 파라미터로 사용자 역할 제어

로그인 후 사이트 `/admin`에 들어간 상태에서 버프로 요청을 가로챕니다.

```
Cookie: Admin=false
```

이 부분을 `Admin=true`로 변경하면 관리자 권한을 얻을 수 있습니다.

### 5-3. 수평적 권한 상승 (Horizontal Privilege Escalation)

```
https://insecure-website.com/myaccount?id=123
```

이는 안전하지 않은 직접 객체 참조(IDOR) 취약점의 예입니다. 이러한 유형의 취약점은 사용자 컨트롤러 매개변수 값을 사용하여 리소스나 함수에 직접 접근할 때 발생합니다.

**실습 단계:**
1. 자신의 계정으로 로그인합니다.
2. Carlos의 글을 찾아 해당 아이디를 클릭합니다.
3. 획득한 URL 형식: `https://domain.net/blogs?userId=e42ec204-e44e-4b9f-b6d6-947ba39182b9`
4. `/my-account`로 돌아가면 자신의 ID 형식을 확인할 수 있습니다.
5. 자신의 ID 형식으로 위 URL의 아이디값을 변경합니다.
6. API 값이 반환되고 이를 제출합니다.

### 5-4. 수평적에서 수직적 권한 상승 (Horizontal to Vertical Privilege Escalation)

로그인 후 ID 값을 `administrator`로 수정합니다. 비밀번호가 나오는데, 버프로 가로챈 패스워드 저장 요청을 확인하면 비밀번호가 저장됩니다.

다시 재로그인하여 administrator 계정으로 로그인한 후, 패널에서 carlos 계정을 삭제합니다.

## 6. 인증 취약점 (Authentication Vulnerabilities)

### 6-1. 무차별 대입을 통한 사용자 이름 찾기

사용자 이름은 이메일 주소처럼 쉽게 알아볼 수 있는 패턴을 따르는 경우 특히 추측하기 쉽습니다.

**일반적인 사용자 이름 패턴:**
- `firstname.lastname@somecompany.com`
- `admin@username.com`
- `administrator`

### 6-2. 사용자 이름 열거 (Username Enumeration)

사용자 이름 열거는 공격자가 웹사이트의 동작 변화를 관찰하여 특정 사용자 이름이 유효한지 여부를 확인하는 방식입니다.

일반적으로 로그인 페이지에서 유효한 사용자 이름을 입력했지만 비밀번호를 잘못 입력했을 때 또는 회원가입 양식에서 이미 사용 중인 사용자 이름을 입력했을 때 발생합니다.

### 6-3. 사용자 이름 열거를 통한 효율적인 브루트 포스 공격

#### 1단계: 사용자 이름 찾기 (Username Enumeration)

**요청 포착:**
- 브라우저에서 아무 아이디나 패스워드를 넣고 로그인 시도
- Burp Suite의 `Proxy > HTTP history`에서 `POST /login` 요청을 찾아 Intruder로 보냅니다

**Payload 위치 지정:**
- Intruder의 Positions 탭에서 `username=§invalid-username§` 부분만 `§` 기호로 감싸기
- 패스워드는 임의의 고정값으로 유지

**공격 설정:**
- Attack type을 **Sniper**로 설정
- Payloads 탭에서 **Simple list** 선택
- 후보 유저네임 리스트를 붙여넣고 `Start attack` 실행

**결과 분석:**
- 새 창에서 **Length** 컬럼을 클릭해 정렬합니다
- 다른 요청들과 길이가 다른 항목 찾기
- 해당 응답을 확인하면, 다른 것들은 "Invalid username"이지만 그 항목만 "Incorrect password"라는 메시지를 반환합니다

#### 2단계: 패스워드 알아내기 (Password Brute-Force)

**위치 재설정:**
- Intruder 탭에서 `Clear §`를 눌러 기존 설정 지우기
- 찾은 유저네임은 고정값으로 입력
- 패스워드 파라미터만 `§`로 감싸기: `username=identified-user&password=§invalid-password§`

**공격 설정:**
- Payloads 탭에서 기존 유저네임 리스트 제거
- 후보 **패스워드 리스트** 붙여넣기
- `Start attack` 실행

**결과 분석:**
- **Status** 컬럼 확인
- 대부분의 요청이 `200` 응답을 반환
- 유일하게 하나만 **`302` (Redirect)** 응답 받음 → 이것이 성공한 패스워드

### 응답 차이를 통한 사용자 정보 판별 팁

#### 답 길이 (Length)
가장 흔하게 활용되는 지표입니다. 유효한 계정이거나 올바른 패스워드일 경우 서버가 반환하는 에러 메시지(예: "Incorrect password" vs "Invalid username")나 성공 페이지의 HTML 구조가 미세하게 달라지면서 바이트 수 차이로 나타납니다.

#### 상태 코드 (Status Code)
- 로그인 성공 시: `302 Found` (또는 `303 See Other`) 상태 코드 반환
- 로그인 실패 시: `200 OK` 유지되며 에러 페이지 표시

#### 응답 시간 (Response Time/Delay)
서버가 내부적으로 올바른 계정일 때만 DB 조회나 추가 로직(예: 비밀번호 해시 검증)을 수행하느라 응답 속도가 미세하게 지연되는 경우가 있습니다.

### 6-4. 2단계 인증 우회 (Bypassing Two-Factor Authentication)

#### 취약점 원인
**서버 측 접근 제어 미흡 (Broken Access Control):** 2단계 인증(2FA) 단계를 거치는 도중, 사용자가 인증 코드 입력 페이지(`/login2` 등)에서 직접 계정 페이지(`my-account`)로 URL을 강제 변경했을 때 서버가 세션의 2FA 완료 여부를 제대로 검증하지 않고 곧바로 페이지 접근을 허용합니다.

#### 실습 진행

**1단계 (정상 로그인 및 URL 파악):**
- 본인 계정으로 로그인
- 2FA 코드를 거쳐 최종 도달하는 계정 페이지의 URL 구조 파악

**2단계 (우회 시도):**
- 로그아웃 후 피해자(Target) 계정의 아이디와 패스워드로 로그인
- 2FA 코드 입력 화면이 나오면, 브라우저 주소창의 URL을 메모해 둔 계정 페이지(`my-account`) 경로로 직접 수정하여 엔터 입력

**3단계 (결과):**
- 서버가 추가 인증 단계를 강제하지 않고 곧바로 마이페이지를 렌더링하면 완료

## 7. SSRF (Server-Side Request Forgery)

### 개요
서버 측 요청 위조(SSRF)는 공격자가 서버 측 애플리케이션에 의도하지 않은 위치로 요청을 보내도록 유도하는 웹 보안 취약점입니다.

일반적인 SSRF 공격에서 공격자는 서버가 조직 인프라 내의 내부 전용 서비스에만 연결하도록 만들 수 있습니다. 또는 서버가 임의의 외부 시스템에 연결하도록 강제할 수도 있습니다. 이로 인해 인증 자격 증명과 같은 민감한 데이터가 유출될 수 있습니다.

### 7-1. 로컬 서버를 대상으로 한 기본 SSRF 공격

#### 1단계: '재고 확인' 요청 가로채기
- 웹사이트의 상품 상세 페이지로 이동
- 페이지 하단의 **"Check stock"** 버튼을 클릭할 때 발생하는 요청을 Burp Suite(Proxy > HTTP history)에서 포착
- Burp Repeater로 보냅니다

#### 2단계: `stockApi` 파라미터 변조 (관리자 페이지 접근)
- Repeater 탭에서 **`stockApi`** 파라미터를 찾습니다
- 해당 파라미터의 값을 외부 접근이 차단된 로컬 주소인 `http://localhost/admin`으로 변경
- **Send**를 눌러 요청 전송
- 오른쪽 Response 창에서 관리자 페이지의 HTML 구조가 고스란히 출력되는 것을 확인

#### 3단계: carlos 계정 삭제 실행
- 응답 HTML 내부에서 `carlos` 사용자를 삭제하는 엔드포인트 찾기 (예: `/admin/delete?username=carlos`)
- `stockApi` 파라미터 값을 최종 타깃 경로인 `http://localhost/admin/delete?username=carlos`로 수정
- 요청을 전송하면 서버가 내부 네트워크를 통해 해당 삭제 요청을 처리

### 7-2. 내부망 IP 스캔을 통한 SSRF (Subnet Brute-forcing)

이 시나리오에서는 단일 `localhost`가 아니라 **내부망 대역(`192.168.0.1 ~ 255`)의 8080 포트**에 관리자 페이지가 숨겨져 있습니다.

Burp Intruder를 활용해 내부 대역 전체를 스캔하여 관리자가 존재하는 정확한 IP를 찾아야 합니다.

**Payload 설정:**
```
stockApi=http://192.168.0.§1§:8080/admin
```

**공격 실행:**
- Payloads 탭에서 **Numbers** 옵션 선택
- 0-255까지 범위 설정하여 실행

**IP 찾는 방법:**
- Length를 클릭해서 정렬
- 수십 개씩 나오는 2581 바이트(또는 대다수와 다른) 사이에서 혼자만 길이가 완전히 다른 행 찾기
- 아까 본 141 바이트처럼 튀는 행이 있다면, 그 행의 Payload 번호가 바로 진짜 관리자 IP의 마지막 숫자

### SSRF 방어 방법

#### 화이트리스트 기반 URL 검증 (Allowlist)
블랙리스트 방식은 우회 기법에 취약하므로, 반드시 허용된 도메인이나 IP 주소 목록만 명시적으로 허용하도록 구현합니다.

#### 사설 IP 및 루프백 대역 차단
입력된 URL이 `127.0.0.1`, `localhost` 같은 루프백 주소나 사설 IP 대역(`10.0.0.0/8`, `192.168.0.0/16`, `172.16.0.0/12`)을 가리키는지 정규식이나 IP 파싱 라이브러리로 검사하여 차단합니다.

#### 위험한 프로토콜(Scheme) 제한
`http`와 `https` 이외에 시스템 파일을 읽거나 다른 프로토콜을 악용할 수 있는 `file://`, `gopher://`, `dict://`, `ftp://` 등의 스킴 사용을 원천 차단합니다.

#### 아웃바운드 트래픽 제어 (Egress Filtering)
방화벽이나 네트워크 정책을 통해 애플리케이션 서버가 불필요한 내부망 대역이나 외부로 향하는 통신을 엄격하게 제한합니다.

#### HTTP 리디렉션 추적 비활성화
외부 URL에 요청을 보냈을 때 서버가 `3xx` 리디렉션을 자동으로 따라가며 내부망을 타격하는 우회 공격을 막기 위해 리디렉션 기능 자체를 끄거나 제한합니다.

#### 내부 서비스 인증 체계 강화
"내부망에 있으니 안전하다"는 신뢰 모델(Implicit Trust)에서 벗어나, 내부 API나 관리자 인터페이스 간 통신에도 별도의 인증 토큰이나 자격 증명을 요구하도록 설계합니다.

## 8. 파일 업로드 취약점 (File Upload Vulnerabilities)

### 개요
보안 관점에서 최악의 시나리오는 웹사이트에서 PHP, Java, Python 파일과 같은 서버 측 스크립트를 업로드할 수 있도록 허용하고, 해당 스크립트를 코드로 실행하도록 설정되어 있는 경우입니다.

### 웹 셸 (Web Shell)

웹 셸은 공격자가 올바른 엔드포인트로 HTTP 요청을 보내는 것만으로 원격 웹 서버에서 임의의 명령을 실행할 수 있도록 하는 악성 스크립트입니다.

웹 셸을 성공적으로 업로드할 수 있다면 서버에 대한 완전한 제어권을 확보하게 됩니다. 즉, 임의의 파일을 읽고 쓸 수 있고, 민감한 데이터를 유출할 수 있으며, 심지어 서버를 이용하여 내부 인프라 및 네트워크 외부의 다른 서버에 대한 공격을 개시할 수도 있습니다.

#### 간단한 파일 읽기 웹 셸
```php
<?php echo file_get_contents('/path/to/target/file'); ?>
```

일단 업로드되면, 이 악성 파일에 대한 요청을 보내면 응답으로 대상 파일의 내용이 반환됩니다.

#### 명령어 실행 웹 셸
```php
<?php echo system($_GET['command']); ?>
```

이 스크립트를 사용하면 다음과 같이 쿼리 매개변수를 통해 임의의 시스템 명령을 전달할 수 있습니다.

```
GET /example/exploit.php?command=id HTTP/1.1
```

### 8-1. 무제한 파일 업로드를 악용하여 웹 셸을 배포하는 방법

#### 취약점 개요
아바타 업로드 기능에서 확장자 검증이 제대로 이루어지지 않아, 이미지 대신 악성 PHP 스크립트 파일을 업로드하고 서버에서 이를 실행(RCE)하여 카를로스의 비밀 파일을 탈취합니다.

#### 단계별 풀이

**1단계: 아바타 업로드 및 확인**
- 웹 계정에 로그인
- 임의의 이미지를 업로드
- 계정 페이지에서 아바타 미리보기가 뜨는 것을 확인

**2단계: 프록시 기록 필터링**
- Burp Suite의 **Proxy > HTTP history**로 이동
- 필터 창을 열고, **MIME type**에서 **Images**만 체크하여 필터 적용

**3단계: Repeater로 요청 전송**
- 기록에서 아바타를 불러오는 `GET /files/avatars/<이미지파일명>` 요청 찾기
- **Repeater**로 보냅니다

**4단계: 악성 PHP 파일 생성**
카를로스의 비밀 파일을 읽어오는 `exploit.php` 파일 생성:

```php
<?php echo file_get_contents('/home/carlos/secret'); ?>
```

**5단계: 파일 업로드**
- 아바타 업로드 기능을 통해 `exploit.php` 파일 업로드
- 업로드 성공 메시지 확인

**6단계: Repeater에서 경로 변경 및 실행**
Repeater로 보냈던 요청의 경로를 업로드한 파일명으로 수정:

```
GET /files/avatars/exploit.php HTTP/2
```

요청을 전송합니다.

**7단계: 비밀 키 획득**
- 요청을 전송하면 서버가 PHP 스크립트를 실행
- 응답으로 카를로스의 비밀 값(Secret)이 반환됩니다
- 이를 제출하여 랩 완료

### 8-2. Content-Type 제한 우회를 통한 웹 셸 업로드

#### 해결 단계

**1단계:** `exploit.php` 파일을 업로드 시도

**2단계:** Burp Suite의 **Proxy > HTTP history**에서 `POST /my-account/avatar` 요청을 찾아 **Repeater**로 보냅니다

**3단계:** Repeater 요청 본문(Body)에서 파일 파트의 `Content-Type` 부분을 **`image/jpeg`** 또는 `image/png`로 수정합니다

```
------WebKitFormBoundarykhfcumnicBMzjpg8
Content-Disposition: form-data; name="avatar"; filename="exploit.php"
Content-Type: image/jpeg

<?php echo file_get_contents('/home/carlos/secret'); ?>
------WebKitFormBoundarykhfcumnicBMzjpg8
```

**4단계:** 요청을 보내 업로드가 성공하는 것을 확인

**5단계:** `GET /files/avatars/exploit.php` 요청을 날려 비밀 키를 획득

## 9. OS 명령 인젝션 (OS Command Injection)

### 실습 단계

#### 1단계: 요청 캡처 및 Repeater 이동
- 웹사이트 상품 상세 페이지에서 **Check stock** 버튼 클릭
- Burp Suite의 **Proxy > HTTP history**에서 해당 요청 찾기
- 우클릭 후 **Send to Repeater** 선택

#### 2단계: `storeId` 파라미터 수정
- Repeater 탭의 요청 데이터 영역에서 `storeId` 값 찾기 (예: `storeId=1`)
- 해당 값을 `storeId=1|whoami`로 변경

파이프 기호 `|`는 앞의 명령어가 끝난 뒤 이어지는 OS 명령어를 연달아 실행하도록 만듭니다.

#### 3단계: 응답 확인
- 상단의 **Send** 버튼을 눌러 요청 전송
- 하단 응답(Response) 창에 현재 시스템의 사용자 이름이 원시 텍스트 형태로 출력되는지 확인

## 10. SQL 인젝션 (SQL Injection)

### 10-1. 기본 SQL 인젝션

#### 제품 카테고리 요청 캡처
- 웹사이트 메인 페이지에서 특정 카테고리(예: Gifts) 클릭
- 발생하는 요청을 Burp Suite(Proxy > Intercept)로 가로채기

#### Repeater로 요청 보내기
- 가로챈 요청을 우클릭하여 **Send to Repeater** 클릭
- Repeater 탭으로 이동

#### `category` 파라미터 조작
요청 중 카테고리를 지정하는 파라미터 값을 **`category=Gifts'+OR+1=1--`** 형태로 수정합니다.

*(이때 따옴표로 기존 쿼리의 문자열을 닫고, `OR 1=1` 조건을 추가하여 항상 참이 되도록 만든 뒤 `-` 주석 처리 기호로 뒤의 쿼리를 무력화합니다.)*

```
GET /filter?category=Tech+gifts'+OR+1=1-- HTTP/2
```

#### 응답 확인
- 상단의 **Send** 버튼을 눌러 요청 전송
- 하단 응답 창에 출시 여부와 상관없이(`released = 1` 조건이 무력화되어) 미출시 제품까지 포함된 여러 제품 목록이 출력되는지 확인

### 10-2. 로그인 우회를 허용하는 SQL 인젝션

#### 공격 단계
1. Burp Suite를 사용하여 로그인 요청을 가로챕니다
2. 매개변수를 수정하여 값을 다음과 같이 지정합니다: `administrator'--`
