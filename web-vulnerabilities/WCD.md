# 웹 캐시 기만(WCD, Web Cache Deception)

## 🛡️ 웹 캐시 기만 (Web Cache Deception, WCD) 요약 노트

한줄요약: 공격자가 캐시 서버와 원본 서버의 URL 처리 차이를 이용해서, 악의적인 응답을 캐시에 저장시키고 그 캐시를 다른 사용자에게 전달하게 만드는 공격

### 1. 개념 정의

- **정의:** 공격자가 원격의 피해자(유저)를 속여, **민감한 동적 정보(개인정보, API 키 등)가 담긴 페이지를 캐시 서버(Cache Server)에 정적 파일로 오인하여 저장(캐싱)하게 만든 뒤 이를 탈취하는 공격**입니다.

### 2. 발생 원인 (핵심 메커니즘)

- **서버 간 URL 해석 불일치(Path Mapping Mismatch):**
    - 프론트엔드의 **캐시 서버**와 백엔드의 **원본 서버**가 URL 경로를 다르게 해석하기 때문에 발생합니다.
    - **원본 서버(백엔드):** REST API 등의 이유로 URL 경로 뒤에 붙은 불필요한 확장자나 세그먼트(예: `/my-account/wcd.css`)를 무시하거나 유연하게 처리하여 유저의 실제 프로필 데이터(HTML/JSON)를 정상 응답합니다.
    - **캐시 서버(프론트엔드):** URL 주소 끝에 붙은 확장자(예: `.css`, `.js`)만 보고 단순하게 "정적 리소스(Static File)"로 판단하여 무조건 캐시에 저장해 버립니다.

### 3. 공격 시나리오 (단계별 흐름)

1. **링크 조작:** 공격자가 피해자에게 확장자가 변조된 악성 링크(예: `http://example.com/my-account/wcd.css`)를 전달하여 클릭하게 유도합니다.
2. **원본 서버 응답:** 백엔드 서버는 뒤의 `.css`를 무시하고 피해자의 로그인된 민감한 정보(프로필, API 키 등)를 응답으로 돌려줍니다.
3. **잘못된 캐싱:** 중간의 캐시 서버는 이 응답을 `.css` 파일로 착각해 **자신의 캐시 스토리지에 피해자의 개인정보를 저장**합니다.
4. **정보 탈취:** 공격자가 동일한 악성 링크로 접속하면, 캐시 서버가 저장해 둔 **피해자의 민감한 정보**를 그대로 응답해주어 계정이나 API 키가 털리게 됩니다.

### 4. 주요 영향 (Impact)

- 세션 토큰, API 키, 개인 신상 정보 등 민감한 유저 데이터 노출
- 권한 상승(Privilege Escalation) 및 계정 탈취로 이어짐

### 5. 대응 및 방어 방안 (Remediation)

- **엄격한 캐시 제어 헤더 사용:** 민감한 동적 페이지 응답에는 반드시 `Cache-Control: no-store` 또는 `private` 헤더를 설정하여 캐시되지 않도록 방지합니다.
- **URL 매핑 일치화:** 캐시 서버와 원본 서버가 URL 경로와 확장자를 동일한 로직으로 파악하도록 규칙을 통일합니다.

**Delimiter discrepancies**

- **핵심 원리**: 원본 서버(백엔드 프레임워크)와 앞단에 있는 캐시 서버(CDN 등)가 URL 주소를 해석하는 방식(구분 기호의 차이)이 서로 달라서 발생하는 틈을 파고드는 공격입니다.
- **구분 기호(Delimiter)의 차이**:
    - **Java Spring 서버**: 세미콜론(`;`)을 '매개변수(Matrix Variable)를 구분하는 기호'로 인식합니다. 그래서 `/profile;foo.css`로 요청이 오면, Spring은 `;` 이후를 잘라내고 순수하게 `/profile`로 해석하여 사용자의 민감한 개인정보를 응답으로 돌려줍니다.
    - **일반 캐시/CDN 서버**: 세미콜론(`;`)을 구분 기호로 보지 않고 **그냥 파일 이름의 일부**로 취급합니다. 즉, 전체 주소 끝이 `.css`로 끝난다고 판단합니다.
- **취약점이 발생하는 이유**:
    1. 캐시 서버는 `.css`로 끝나는 요청을 받으면 "이건 누구나 봐도 되는 정적 디자인 파일이네?" 하고 자물쇠를 채워 캐시에 저장(Cache)해 버립니다.
    2. 하지만 실제 원본 서버가 준 응답은 특정 사용자의 민감한 개인정보(`/profile`)입니다.
    3. 결과적으로 다른 사람이 그 주소로 접근하면, 캐시 서버가 저장해 둔 다른 사람의 개인정보(CSS 파일로 오인된 데이터)를 그대로 받아보게 되어 정보가 털리게 됩니다.

즉, "서버는 `어? 이건 내 정보(프로필)를 달라는 거네` 하고 정상 응답을 줬는데, 앞단의 캐시는 `어? 이거 확장자가 .css(정적파일)네? 저장해야지!` 하고 엉뚱하게 저장해 버려서 생기는 착시 현상"이라고 이해하시면 됩니다.

**테스트의 핵심 흐름**

- **구분 기호 뒤에 확장자 붙이기**: 원본 서버가 인식하는 특정 구분 기호(예: `;`, `#`, `?` 등) 뒤에 의도적으로 `.css`나 `.js` 같은 정적 확장자를 붙여서 서버로 요청을 보냅니다.
- **캐시 여부 판단하기**: 만약 서버 응답이 캐시(Cache Hit)되었다면, 이는 "캐시 서버가 해당 구분 기호를 인식하지 못하고, 확장자(`.css`) 규칙에 걸려 민감한 페이지 내용을 그대로 캐시에 저장해 버렸다"는 결정적인 증거가 됩니다.
- **다양한 조합 검증**: 완벽한 취약점 포인트를 찾기 위해 특수문자 및 ASCII 문자 전반의 잠재적 구분 기호들과 다양한 확장자(`.css`, `.js`, `.ico`, `.png` 등)를 바꿔가며 테스트를 수행합니다.

1. PortSwigger의 **웹 캐시 기만(Web Cache Deception) - 구분 기호 불일치(Delimiter Discrepancies)** 랩입니다.

공격의 전체 흐름과 각 단계별 실습 방법입니다.

### 핵심 매커니즘

- **원본 서버**: `;`를 구분 기호로 인식하므로 `/my-account;wcd.js` 요청이 오면 `;` 뒷부분을 무시하고 `/my-account` 페이지(마이페이지 개인정보)를 응답함.
- **캐시 서버**: `;`를 구분 기호로 보지 않고 일반 문자열로 취급. 전체 주소 끝이 `.js`로 끝나므로 **정적 스크립트 파일**로 판단하여 민감한 개인정보가 담긴 응답을 캐시에 저장해 버림.

### 단계별 풀이 가이드

**1. 원본 서버의 구분 기호(Delimiter) 찾기**

1. Burp 내장 브라우저로 랩 접속 후 `wiener : peter` 계정으로 로그인합니다.
2. `Proxy > HTTP history`에서 `GET /my-account` 요청을 찾아 **Repeater**와 **Intruder**로 보냅니다.
3. Intruder로 이동하여 페이로드 위치를 지정합니다: `/my-account§§abc`
4. Payloads 설정에서 준비된 구분 기호 문자 목록(PortSwigger 제공)을 붙여넣습니다.
5. **Payload Encoding** 항목의 `URL-encode these characters` **체크를 해제**합니다. (특수문자가 `%3B` 등으로 인코딩되지 않고 그대로 날아가야 함)
6. **Start attack** 클릭 후 결과를 Status code로 정렬하면, `;`와 `?`를 넣었을 때만 **200 OK**가 떨어지며 API 키가 반환되는 것을 확인할 수 있습니다. (서버가 `;`와 `?`를 구분 기호로 쓴다는 뜻)

**2. 캐시 서버와의 불일치 검증**

1. Repeater로 돌아와 `GET /my-account?abc.js`를 전송합니다. -> 응답 헤더에 캐시 관련 흔적이 남지 않음 (`?`는 캐시 서버도 구분 기호로 인식함).
2. 경로를 `GET /my-account;abc.js` (또는 `;wcd.js`)로 바꾸어 전송합니다. -> 응답 헤더에 `X-Cache: miss`가 찍힙니다.
3. 동일한 요청을 **한 번 더 전송**합니다. -> 응답 헤더가 `X-Cache: hit`으로 바뀝니다!
    - **의미**: 캐시 서버는 `;`를 구분자로 인식하지 않아 전체를 `.js` 파일 요청으로 오인하고 응답을 저장한 것입니다.

**3. 악성 익스플로잇 페이로드 작성 및 전달**

1. 상단의 **Go to exploit server** 버튼을 클릭합니다.
2. **Body** 란에 피해자(`carlos`)가 해당 주소로 접속하도록 유도하는 자바스크립트 코드를 작성합니다.
    - *주의: 고유한 캐시 키 생성을 위해 앞서 테스트한 문자열과 다르게 작성해야 합니다.*

#### body에 넣을값

```
<script>
  document.location = "https://YOUR-LAB-ID.web-security-academy.net/my-account;wcd.js";</script>
```

1. **Deliver exploit to victim** 버튼을 누릅니다. 피해자가 이 페이지를 열면서 피해자의 개인정보(`/my-account`)가 `.js` 캐시로 저장됩니다.

**4. API 키 탈취 및 제출**

1. 브라우저 주소창에 피해자가 탈취당한 주소(`https://YOUR-LAB-ID.web-security-academy.net/my-account;wcd.js`)로 직접 접속합니다.
2. 캐시 서버에 남아 있는 **`carlos`의 API 키**가 화면에 출력되는 것을 확인하고 복사합니다.
3. 상단의 **Submit solution**을 눌러 복사한 API 키를 제출하면 랩이 완료됩니다.

**X-Cache: hit의 의미**
요청한 데이터가 원본 서버(백엔드)까지 가지 않고, 앞단에 있는 **캐시 서버(CDN 등)의 저장소에 이미 보관되어 있어 거기서 바로 가져다주었다**는 뜻입니다. 반대로 처음 요청했을 때 뜨는 `X-Cache: miss`는 캐시에 데이터가 없어 원본 서버에 직접 요청해 받아왔다는 뜻입니다.

**왜 두 번 보내야 하는가?**
첫 번째 요청과 두 번째 요청은 각각 수행하는 역할이 다릅니다.

- **첫 번째 요청 (Miss)**: 캐시 서버에 해당 주소가 아직 없으므로 원본 서버로 요청을 보내 응답을 받아옵니다. 이때 캐시 서버는 이 응답을 자기 저장소에 새로 저장(Caching)합니다.
- **두 번째 요청 (Hit)**: 방금 저장된 캐시가 정상적으로 작동하는지 확인하는 단계입니다. 여기서 `hit`이 뜬다면, 캐시 서버가 이 요청(예: 확장자가 `.js`로 끝나는 민감한 페이지)을 **정적 파일로 착각해서 캐시에 확실하게 저장해 두었다**는 결정적인 증거가 됩니다.

이 두 번째 `hit`이 확인되어야만, 나중에 피해자가 그 주소에 접속했을 때 피해자의 민감한 정보가 캐시 서버에 안전하게 박제되고, 공격자가 그걸 훔쳐볼 수 있는 상태가 완성됩니다.

'정규화 불일치(Normalization Discrepancy)'를 설명하는 핵심 내용입니다.

- **정규화(Normalization)란?**: URL 경로에 섞여 있는 인코딩된 문자(예: `%2f`)를 원래 기호(`/`)로 디코딩하거나, 점 두 개(`..`) 같은 상위 폴더 이동 경로를 해석하여 주소를 깔끔하게 정리·표준화하는 과정입니다.
- **불일치의 핵심**: 앞단에 있는 **캐시 서버**와 뒷단의 원본 서버(백엔드)가 이 URL을 해석하고 정리하는 방식(파싱 방식)의 차이에서 취약점이 발생합니다.
- **예시 분석 (`/static/..%2fprofile`)**:
    - **브라우저의 역할**: 슬래시를 그대로 쓰면 브라우저가 먼저 해석해 버리기 때문에, 의도적으로 `%2f`(슬래시의 URL 인코딩 값)를 사용해 인코딩된 상태로 요청을 보냅니다.
    - **캐시 서버의 동작**: `%2f`를 제대로 디코딩하지 못하거나 `..` 세그먼트를 처리하지 못해, 이 요청을 여전히 `/static/` 아래에 있는 일반 파일 요청으로 취급합니다. 캐시 서버에는 *"`/static/`으로 시작하는 요청은 정적 파일로 보고 무조건 캐시해라"*라는 규칙이 걸려 있기 때문에 이 응답을 저장해 버립니다.
    - **원본 서버의 동작**: `%2f`를 슬래시(`/`)로 디코딩하고 `..`를 해석해 상위 디렉토리로 이동합니다. 결과적으로 이 요청을 `/profile`(사용자의 민감한 개인정보 페이지)로 해석하여 정상적인 개인정보 데이터를 응답으로 돌려줍니다.
- **최종 결과**: 원본 서버는 사용자의 민감한 프로필 정보를 줬는데, 캐시 서버는 이를 `/static/` 폴더 안의 무해한 정적 파일인 줄 알고 캐시에 덜컥 저장해 버리는 참사가 발생합니다.

즉, "서버는 주소를 똑똑하게 해석해서 내 개인정보를 줬는데, 앞단에서 주소를 멍청하게 해석하는 캐시 서버가 이걸 정적 파일로 착각해 외부에 박제해 버리는 현상"을 뜻합니다.

**인코딩 위치가 중요한 이유 (팁)**

- CDN이나 캐시 서버는 슬래시(`/`) 위치를 기준으로 정적 디렉터리 규칙(예: `/static/`로 시작하는가?)을 엄격하게 검사합니다.
- 이 때문에 점 세그먼트 전체를 인코딩하느냐, 슬래시만 인코딩하느냐(`..%2f` vs `%2e%2e%2f`)에 따라 앞단의 캐시 서버와 뒷단의 원본 서버가 각각 이 주소를 완전히 딴판으로 쪼개서 해석하게 되며, 이 틈새가 바로 치명적인 웹 캐시 기만(WCD) 공격의 무기가 됩니다.

CDN (Content Delivery Network, 콘텐츠 전송 네트워크)은 전 세계 여러 지역에 분산 배치된 캐시 서버(엣지 서버) 네트워크를 통해, 사용자와 물리적으로 가장 가까운 곳에서 웹 사이트의 콘텐츠(이미지, 동영상, CSS, JS 등)를 빠르게 전달해 주는 분산 인프라 서비스입니다.

- **속도 향상 및 로딩 최적화**: 원본 서버(Origin Server)가 멀리 있더라도 사용자와 가장 가까운 거리에 있는 CDN 서버가 캐시된 데이터를 대신 보내주기 때문에 웹페이지 로딩 속도가 획기적으로 빨라집니다.
- **서버 부하 분산**: 대규모 트래픽이나 디도스(DDoS) 공격이 발생했을 때, 수많은 요청을 여러 CDN 서버로 분산시켜 원본 서버가 다운되는 것을 막아주는 방패 역할을 합니다.
- **보안 기능**: SSL/TLS 인증서 처리, 웹 방화벽(WAF), 봇 차단 등 앞단에서 기본적인 보안 필터링을 수행합니다. (Cloudflare, AWS CloudFront, Akamai 등이 대표적입니다.)

앞서 살펴본 **웹 캐시 기만(WCD) 취약점**에서 원본 서버 앞단에 서서 민감한 페이지를 '정적 파일'로 착각하고 덜컥 캐시에 저장해 버리는 주체가 바로 이 **CDN**입니다. 인프라 구축과 보안 진단 모두에서 핵심적으로 다뤄지는 이유가 여기에 있습니다.

**핵심 메커니즘**

- **원본 서버**: `%23`(URL 인코딩된 `#`)이나 `?`를 **구분 기호**로 인식하기 때문에, `/my-account%23...`로 요청이 와도 앞쪽의 `/my-account`로 해석해서 사용자의 민감한 API 키를 정상 응답해 줍니다.
- **캐시 서버**: 이 복잡한 경로를 정규화하거나 처리할 때, 캐시 규칙에 맞는 정적 경로(`resources`)와 엮여 있는 것으로 오인하여 피해자의 개인정보 응답을 캐시에 덜컥 저장해 버립니다.

**실행 단계별 가이드**

- **1단계: 엔드포인트 및 구분 기호 확인**
    1. `wiener:peter`로 로그인하여 내 API 키를 확인합니다.
    2. `GET /my-account` 요청을 **Intruder**로 보내고, 경로 뒤에 `§§abc`를 붙여 퍼징합니다.
    3. 페이로드로 특수문자들을 넣고 **인코딩 체크를 해제**한 뒤 실행하면, `#`, `?`, `%23`, `%3f`에서 200 OK가 떨어지는 것을 볼 수 있습니다. (브라우저가 `#`을 가로채는 것을 막기 위해 인코딩된 형태인 `%23`을 사용합니다.)
- **2단계: 익스플로잇 페이로드 조합하기**
    
    원본 서버는 내 정보를 주게 만들고, 캐시 서버는 이걸 정적 리소스로 착각해 캐시하게 만드는 최종 주소를 조합합니다.
    
    `/my-account%23%2f%2e%2e%2fresources?wcd`
    
- **3단계: 익스플로잇 서버에 등록하고 피해자 유도하기**HTML
    1. 랩 안의 **Go to exploit server**로 이동합니다.
    2. Body에 아래 코드를 넣고 피해자(`carlos`)에게 전달합니다. (뒤에 붙은 `?wcd`는 고유 캐시를 만들기 위한 캐시 버스터입니다.)
    
    #### body
    
    ```
    <script>
      document.location = "https://YOUR-LAB-ID.web-security-academy.net/my-account%23%2f%2e%2e%2fresources?wcd";</script>
    ```
    
    1. **Deliver exploit to victim**을 클릭합니다.
- **4단계: API 키 탈취**
    
    피해자가 공격을 당한 뒤, 브라우저 주소창에 방금 그 주소로 직접 들어가면 **carlos의 API 키**가 화면에 나타납니다. 이를 복사해 제출하면 완료됩니다.

## 결론

## **웹 캐시 기만 취약점 방지**

웹 캐시 기만 취약점을 방지하기 위해 다음과 같은 다양한 조치를 취할 수 있습니다.

- 동적 리소스를 표시할 때는 항상 `Cache-Controlno-storeprivate`헤더를 사용하고, 지시문과 함께 설정하십시오
- 캐싱 규칙이 헤더를 덮어쓰지 않도록 CDN 설정을 구성하세요 `Cache-Control`
- `Content-Type` CDN에서 제공하는 웹 캐시 기만 공격 방지 기능을 활성화하세요. 많은 CDN에서는 응답이 요청 URL의 파일 확장자와 일치하는지 확인하는 캐시 규칙을 설정할 수 있습니다 . 예를 들어, Cloudflare의 Cache Deception Armor를 사용할 수 있습니다.
- 원본 서버와 캐시가 URL 경로를 해석하는 방식에 불일치가 없는지 확인하십시오.
